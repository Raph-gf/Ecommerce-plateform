Phase 1 — Auth Feature

Backend Concepts

Everything you built in the auth feature, explained from first principles. Read this between sessions to reinforce what you learned by doing.

★ Why NestJS Exists

Before NestJS, Node.js backends were built with Express. Express is powerful but gives you zero structure. You can put your database query in a route handler, your business logic in a middleware, your config in a random file. It works, but as the app grows it becomes a mess that only the original author can understand.

NestJS was created to solve this. It asks the question: "What if we enforced a clear structure from day one?" It takes inspiration from Angular (the frontend framework) and brings the same architectural discipline to the backend.

💡
The core promise of NestJS

Any NestJS developer can open any NestJS project and immediately know where to find things — because the structure is always the same. Controllers handle HTTP. Services handle logic. Modules organize features. This is not a suggestion, it's the architecture.

Think of it this way: Express is like an empty plot of land. You can build anything, any way you want. NestJS is like a building with a fixed floor plan — you know exactly where the kitchen, bedroom, and bathroom go. Less freedom, but a much better home.

★ How to Think in NestJS

The biggest mental shift coming from Express or Laravel is this: stop thinking in files, start thinking in responsibilities.

Every time you write code, ask yourself one question:

🤔
"What is the responsibility of this code?"

Is it handling an HTTP request? → Controller.
Is it business logic or a database query? → Service.
Is it organizing a feature? → Module.
Is it deciding who can access a route? → Guard.
Is it transforming the response shape? → Interceptor.
Is it catching errors? → Filter.

In Laravel, you might write a database query directly in a controller. In NestJS, that would be wrong — even if it works. The database query belongs in a service. The controller only calls the service and returns the result. This isn't just style — it has real consequences:

If logic is in the right place...You can...
Business logic in a ServiceUnit test it without HTTP, without a database
Auth logic in a GuardApply it to any route with one decorator
Response transformation in InterceptorChange API response shape for the whole app in one place
Error handling in a FilterGet consistent error responses everywhere automatically

The mental model in one sentence

NestJS is a system of specialized workers, each with one job. A request walks through the assembly line, and each worker does their specific task. Your job as a developer is to put the right code in the right worker.

★ The Layer System

NestJS has a strict concept of layers. Each layer only communicates with the layer directly next to it. You never skip layers.

HTTP Request
     ↓
Controller          ← knows about HTTP (requests, responses, cookies, headers)
     ↓
Service             ← knows about business rules (NO knowledge of HTTP)
     ↓
Repository/Prisma   ← knows about the database (NO knowledge of business rules)
     ↓
Database
🚫
Never skip layers

A controller should never query the database directly. A service should never know about HTTP status codes or cookies. A Prisma query should never contain business logic. When you skip a layer, you create code that's impossible to test and painful to change.

What "no knowledge of HTTP" means in practice

Look at your AuthService. It throws HttpException with status codes. Strictly speaking, this is a violation — a service shouldn't know about HTTP. But in NestJS it's a widely accepted pragmatic choice because HttpException is just a way to signal error types. The important rule is: your service should never touch request or response objects directly. Those belong only in controllers.

★ The Dependency Injection Mindset

Dependency Injection is the heart of NestJS. It sounds complicated but the idea is simple:

✅
The DI principle

A class should never create its own dependencies. It should declare what it needs and let the framework provide them.

Why does this matter? Because when a class creates its own dependencies, you can never replace them. Consider:

// Without DI — impossible to test, tightly coupled:
class AuthService {
  private prisma = new PrismaService();  // hardcoded — can never be swapped

  async register() {
    await this.prisma.user.create(...);  // always hits real DB
  }
}

// With DI — testable, loosely coupled:
class AuthService {
  constructor(private prisma: PrismaService) {}  // injected from outside

  async register() {
    await this.prisma.user.create(...);  // uses whatever was injected
  }
}
// In tests: inject a fake PrismaService → no real DB needed
// In production: NestJS injects the real PrismaService automatically

This is exactly why your unit tests work — you inject mockPrismaService instead of the real one, and AuthService doesn't know the difference. It just uses whatever it was given.

How NestJS manages DI

NestJS maintains an IoC container (Inversion of Control). When the app starts, it reads all your modules and builds a map of every provider and what it needs. Then it creates instances in the right order and wires everything together. You never call new AuthService() yourself — NestJS does it.

// You declare the dependency:
constructor(private readonly authService: AuthService) {}

// NestJS reads this and thinks:
// "AuthController needs AuthService."
// "AuthService needs PrismaService, JwtService, ConfigService."
// "I'll create them all in the right order and wire them up."

★ Decorators Are Instructions, Not Logic

Decorators are one of the most confusing parts of NestJS for beginners. Here's the key insight:

💡
A decorator doesn't do anything by itself

It attaches metadata (information) to a class, method, or parameter. NestJS reads that metadata at startup or at request time and acts on it.

Think of decorators as sticky notes you put on your code. The sticky note says "this is a controller" or "this route is public" or "inject the current user here". NestJS reads all the sticky notes and wires everything up accordingly.

@Controller('auth')
// Sticky note: "This class handles routes starting with /auth"

@Public()
// Sticky note: "This route doesn't need authentication"
// The JwtAuthGuard reads this note and skips auth

@CurrentUser('userId')
// Sticky note: "Inject request.user.userId into this parameter"
// createParamDecorator reads this and extracts the value

@ResponseMessage('User registered successfully')
// Sticky note: "Use this as the message in the response"
// TransformInterceptor reads this note via Reflector

This is why Reflector exists — it's the tool that reads the sticky notes (metadata) at runtime.

Decorator execution order

When you stack multiple decorators, they execute bottom-up:

@Public()            // ← executes second
@Post('login')       // ← executes first
async login() {}

In practice this rarely matters for NestJS decorators, but it's good to know.

★ The Golden Rules

If you internalize these six rules, you will always know where to put your code in NestJS:

1 Controllers only route Receive request → call service → return result. No business logic, no DB queries.
2 Services own the logic All business rules, all DB queries, all decisions live here. No HTTP knowledge.
3 Modules define boundaries A module owns its providers. Other modules can only use what's explicitly exported.
4 Never new() your dependencies Always declare them in the constructor and let NestJS inject them.
5 Cross-cutting concerns go in guards/interceptors/filters Auth, logging, response shaping, error handling — once, globally, not in every controller.
6 Decorators are metadata, not magic They attach information. Something else (a guard, interceptor, or NestJS itself) reads and acts on it.
🎯
The question to always ask

When you don't know where to put something, ask: "What is the single responsibility of this code?" The answer tells you exactly which NestJS concept it belongs to.

1 Modules

A module is a self-contained unit of your application. Every feature you build lives inside a module. NestJS uses modules to organize code and manage what can be shared between features.

@Module({
  imports:     [...],  // other modules this one depends on
  controllers: [...],  // handle HTTP requests
  providers:   [...],  // services, strategies, guards
  exports:     [...],  // what other modules can use from here
})
export class AuthModule {}
💡
Key rule

A module can only use providers declared in its own providers array, or imported from another module via imports. This is how NestJS enforces encapsulation.

Global Modules

Adding @Global() makes a module available everywhere without importing it explicitly. You used this for PrismaModule so every module can access the database without adding it to their imports.

@Global()
@Module({ providers: [PrismaService], exports: [PrismaService] })
export class PrismaModule {}

2 Controllers

Controllers handle incoming HTTP requests and return responses. They contain no business logic — they just receive input, call a service, and return output.

@Controller('auth')        // base route prefix → /auth
export class AuthController {

  @Post('login')           // → POST /auth/login
  async login(@Body() dto: LoginDto) {
    return this.authService.signIn(dto.email, dto.password);
  }

  @Get('profile/me')       // → GET /auth/profile/me
  async me(@CurrentUser('userId') userId: string) {
    return this.authService.getUserProfile(userId);
  }
}
⚠️
Controller ≠ Business Logic

If you find yourself writing database queries or complex conditions inside a controller, that code belongs in a service instead.

3 Services & Dependency Injection

Services contain business logic. They are injectable — NestJS creates one instance and shares it wherever it's needed.

@Injectable()
export class AuthService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly jwtService: JwtService,
  ) {}
}

What is Dependency Injection?

DI means your classes don't create their own dependencies — NestJS provides them. You declare what you need in the constructor, and the framework handles the rest.

// Without DI — you manage everything manually:
const service = new AuthService(
  new PrismaService(),
  new JwtService(),
);

// With DI — NestJS handles it:
constructor(private authService: AuthService) {}
💡
Why DI matters

It makes your code testable. In tests, you can inject fake (mock) versions of dependencies instead of real ones. It also keeps classes decoupled — they don't know how their dependencies are built.

4 Request Lifecycle

Every HTTP request passes through these layers in a fixed order. Understanding this is essential for knowing where to put your code.

1 Middleware cookie-parser, cors — runs before everything
2 Guards JwtAuthGuard, ThrottlerGuard — can reject with 401/429
3 Interceptors (before) TransformInterceptor — runs before handler
4 Pipes ValidationPipe — validates & transforms DTOs
5 Controller Handler Your method runs here
6 Service Business logic, DB queries
7 Interceptors (after) TransformInterceptor — wraps the response
8 Exception Filters HttpExceptionFilter — catches errors, formats them
✅
Why this matters

Guards run before your controller — they can block the request entirely. Exception filters run last — they catch errors from anywhere above. Interceptors wrap everything — they see both the request going in and the response coming out.

5 Password Hashing

Never store passwords in plain text. Hashing is a one-way operation — you can verify a password but you can't reverse a hash back to the original.

import { hash, compare } from 'bcryptjs';

// When user registers — hash before storing:
const password_hash = await hash(password, 10);
// "MyPassword123!" → "$2b$10$K8ZpkQa..."

// When user logs in — compare without reversing:
const isValid = await compare(plaintext, stored_hash);
// returns true or false

What is a Salt?

bcrypt adds random data (a "salt") before hashing. This means two identical passwords produce completely different hashes, preventing attackers from using precomputed tables (rainbow tables) to crack passwords.

The 10 in hash(password, 10) is the number of salt rounds. Higher = slower = more secure. 10 is the standard for production.

🚫
Never do this

Don't use MD5, SHA1, or SHA256 for passwords — they're fast, which makes them easy to brute force. Only use bcrypt, argon2, or scrypt for passwords.

6 JWT — JSON Web Tokens

A JWT is a self-contained token that carries information (called claims). It has three parts separated by dots:

header.payload.signature
eyJhbGci...  .  eyJzdWIi...  .  SflKxwRJs...
PartContentPurpose
HeaderAlgorithm (HS256)Tells how to verify the signature
Payload{ sub, email, role }Data you put in — readable by anyone
SignatureHMAC of header+payloadProves the token wasn't tampered with
⚠️
The payload is not secret

Anyone can decode the payload — it's just Base64 encoded, not encrypted. The signature is what makes it trustworthy. Never put sensitive data (passwords, card numbers) in a JWT.

// Signing a token:
await jwtService.signAsync(
  { sub: userId, email, role },
  { expiresIn: '1h' }
);

// Verifying a token:
await jwtService.verifyAsync(token, { secret: JWT_SECRET });
// → throws if invalid or expired
// → returns decoded payload if valid

7 Access vs Refresh Tokens

Access TokenRefresh Token
TTL15min – 1h7 – 30 days
StoredMemory (JS variable)httpOnly cookie
Sent withEvery API requestOnly to /auth/refresh
ContainsuserId, email, roleOnly userId
If stolenAttacker has 1h accessAttacker can get new access tokens

Why two tokens?

Short-lived access tokens limit damage if stolen — they expire quickly. Long-lived refresh tokens avoid constant re-login. The refresh token is stored in an httpOnly cookie so JavaScript (and therefore XSS attacks) can never read it.

8 Token Rotation

Every time you use a refresh token, the server deletes it and issues a new one. This is called rotation.

1 Client sends refresh token via httpOnly cookie to POST /auth/refresh
2 Server verifies JWT signature confirms token is valid and not expired
3 Server finds hash match in DB bcrypt.compare() against all stored hashes
4 Old token deleted from DB it can never be used again
5 New token pair issued new access token + new refresh token
💡
Why rotation matters

If someone steals a refresh token and uses it, the legitimate user's next refresh attempt will fail — that token was already rotated. This alerts you to a potential breach and the attacker's token becomes useless.

response.cookie('refresh_token', token, {
  httpOnly: true,    // JS cannot read this → prevents XSS theft
  secure: true,      // HTTPS only → prevents interception
  sameSite: 'strict', // same origin only → prevents CSRF
  maxAge: 7 * 24 * 60 * 60 * 1000, // 7 days in ms
});
⚠️
cookie-parser is required

Without app.use(cookieParser()) in main.ts, request.cookies is undefined. Always register it before testing cookie-based features.

10 Passport & JWT Strategy

Passport is an authentication middleware. In NestJS it integrates via strategies — each strategy handles one way of authenticating (JWT, Google OAuth, local credentials, etc.).

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(private configService: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      secretOrKey: configService.get('JWT_SECRET'),
    });
  }

  validate(payload: any) {
    // Called AFTER Passport verifies the token
    // payload is already decoded and trusted
    return { userId: payload.sub, email: payload.email, role: payload.role };
    // return value → attached to request.user
  }
}
1 Request arrives with Authorization: Bearer <token>
2 Passport extracts token via ExtractJwt.fromAuthHeaderAsBearerToken()
3 Passport verifies signature using secretOrKey — throws if invalid/expired
4 validate() called receives decoded payload { sub, email, role }
5 Return value → request.user available in controller via @CurrentUser()

11 Guards

Guards decide whether a request should proceed. They return true to allow or throw an exception to reject. They run before the controller, after middleware.

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private reflector: Reflector) { super(); }

  canActivate(context: ExecutionContext) {
    // Check if route is marked @Public()
    const isPublic = this.reflector.getAllAndOverride('isPublic', [
      context.getHandler(),
      context.getClass(),
    ]);
    if (isPublic) return true;         // skip auth
    return super.canActivate(context);  // run JWT strategy
  }
}

Registering Guards Globally

// In app.module.ts — keeps guard inside DI container
providers: [
  { provide: APP_GUARD, useClass: JwtAuthGuard },
  { provide: APP_GUARD, useClass: ThrottlerGuard },
]

// NOT this — guard can't inject services like Reflector:
app.useGlobalGuards(new JwtAuthGuard());

12 Interceptors

Interceptors wrap the request/response cycle. They run before AND after the controller handler, giving them the ability to transform both incoming requests and outgoing responses.

@Injectable()
export class TransformInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    // BEFORE: runs before controller

    return next.handle().pipe(
      map(data => {
        // AFTER: transforms the response
        return { data, success: true, message: '...' };
      })
    );
  }
}

How Reflector works

Reflector reads metadata that decorators attached to routes. It's how your interceptor knows what message to use for each endpoint.

// 1. Decorator sets metadata on the route:
@ResponseMessage('User registered successfully')
// internally calls: SetMetadata('response_message', 'User registered successfully')

// 2. Interceptor reads it:
const message = this.reflector.get(
  'response_message',
  context.getHandler()
);

13 Exception Filters

Filters catch exceptions thrown anywhere in the pipeline and format the error response consistently.

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse();
    const status = exception.getStatus();

    response.status(status).json({
      statusCode: status,
      success: false,
      message: exception.message,
      timestamp: new Date().toISOString(),
    });
  }
}
💡
Without a filter

NestJS returns its own default error format which you can't control. With a filter, every error in your app has the exact same consistent shape.

14 Custom Decorators

Parameter Decorators — createParamDecorator

Extract data from the request and inject it directly into controller method parameters.

export const CurrentUser = createParamDecorator(
  (data: keyof UserPayload | undefined, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest<{ user: UserPayload }>();
    return data ? request.user[data] : request.user;
  }
);

// Usage in controller:
async logout(@CurrentUser('userId') userId: string) {}
async me(@CurrentUser() user: UserPayload) {}

Metadata Decorators — SetMetadata

Attach metadata to a route that guards or interceptors can read via Reflector.

// Just a flag — no value needed:
export const Public = () => SetMetadata('isPublic', true);

// With a value:
export const ResponseMessage = (msg: string) =>
  SetMetadata('response_message', msg);

15 DTOs & Validation

DTO (Data Transfer Object) defines the expected shape of incoming request data. ValidationPipe automatically validates incoming requests against the DTO before they reach your controller.

export class RegisterDto {
  @IsEmail()
  email: string;

  @MinLength(8)
  @Matches(/^(?=.*\d)(?=.*[!@#$%^&*])/, {
    message: 'Must contain a number and special character'
  })
  password: string;
}

ValidationPipe with whitelist: true also strips any extra fields not defined in the DTO — protecting you from unexpected data in the request body.

16 Prisma ORM

Prisma is a type-safe database client. It generates TypeScript types from your schema, so you get full autocomplete and type checking on every query.

// Find with relation (JOIN):
const user = await prisma.user.findUnique({
  where: { id: userId },
  include: { refresh_tokens: true },
});

// Exclude a field from the result:
const user = await prisma.user.findUnique({
  where: { id: userId },
  omit: { password_hash: true },  // actually removed from the object
});

// Delete all matching records:
await prisma.refreshToken.deleteMany({
  where: { user_id: userId }
});
🚫
Cast ≠ Omit

user as Omit<User, 'password_hash'> is a lie to TypeScript — the field is still in the object and still sent to the client. Use Prisma's omit option to actually remove the field from the query result.

17 Security Patterns

User Enumeration Prevention

Never reveal which field was wrong on login. Always return the same generic message.

// ❌ Reveals which emails exist in your system:
if (!user) throw new Error('Email not found');
if (!valid) throw new Error('Wrong password');

// ✅ Reveals nothing useful to an attacker:
throw new HttpException('Invalid credentials', 401);

Never Store Raw Tokens

// ✅ Hash before storing:
const token_hash = await hash(refresh_token, 10);
await prisma.refreshToken.create({ data: { token_hash } });

// ✅ Compare to verify:
await compare(incoming_token, stored_hash);

Rate Limiting

// Stricter limit on auth endpoints:
@Throttle({ short: { ttl: 300_000, limit: 10 } })
// → max 10 attempts per 5 minutes
// → returns HTTP 429 when exceeded

18 Environment Variables

Never hardcode secrets in your code. Use environment variables for anything that changes between environments or that must be kept private.

# .env
JWT_SECRET=your_long_random_secret
JWT_EXPIRES_IN=1h
JWT_REFRESH_SECRET=another_long_secret
JWT_REFRESH_EXPIRES_IN=7d
DATABASE_URL=postgresql://...
// getOrThrow preferred for required variables:
configService.getOrThrow('JWT_SECRET')
// → returns string or throws at startup
// → fail fast rather than failing silently later
⚠️
CWD matters

ConfigModule looks for .env in the current working directory when the process starts. In a Turborepo, that's the app's own folder (apps/api/). Put your .env there.
